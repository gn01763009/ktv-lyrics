# KTV 字幕層 Mac App 設計文件

日期：2026-11-08
狀態：待確認

本文標記方式：**【決定】** 是提案人明確說過的；**【判斷】** 是撰寫者的推測或預設，提案人可以推翻；**【實測】** 是在提案人的 Mac（M1、16GB、macOS 26.4.1）或公開資料上量到的。

## 1. 想做什麼、為什麼

邊寫 code 邊唱歌。使用者一邊開著 Claude session、Codex、Claude Desktop、Chrome、Discord、Slack、GitHub、YouTube、Notion、Blender 工作，一邊想跟著正在聽的歌唱，字幕就像 KTV 那樣直接「印」在電腦畫面上。

重點是好玩、有 KTV 的味道，而且完全不妨礙工作。使用者不需要準備字幕，照常放歌就會自動出現。

## 2. 目標

- 【決定】透明字幕浮在所有 app 上，滑鼠可以點穿，不影響後面的任何操作。
- 【決定】自動跟著使用者正在聽的歌，不用手動加字幕。
- 【決定】可以在 app 裡調整位置、大小、顏色、樣式等。
- 【決定】KTV 風格：白字黑邊、唱到的部分變成藍字白邊、上下兩行交錯，參考提案人提供的截圖。
- 【決定】片頭字卡：歌名加原唱、作詞、作曲。
- 【決定】開唱前的星星倒數，可帶「男：」「女：」標記，例如「男：★★★★」。
- 【決定】偶爾在空白處出現《來賓請掌聲鼓勵》。
- 【決定】第一版就要逐字變色（限有逐字資料的歌）。
- 【決定】第一版支援 YouTube，準度以盡力為主，靠手動微調。
- 【決定】做成 Mac app，開源放在 GitHub，讓別人可以照教學安裝。
- 【決定】不付費，不申請 Apple Developer 帳號。

### 成功的樣子

- 在 Spotify、Apple Music、YouTube 放歌，幾秒內出現字幕，不用操作。
- 唱起來覺得字幕跟得上，快轉、暫停、重播、換歌時字幕立刻跟上（YouTube 的準度靠手動微調）。
- 寫 code 時完全感覺不到它擋路，點得到字幕後面的東西，焦點不會被搶走。
- 工程師看 GitHub README，幾分鐘內裝好。

## 3. 不做的事

第一版不做：

- Chrome extension（點穿和透明都做不到，也抓不到桌面版播放器）。
- 讓 YouTube 的準度和 Spotify 一樣（需要另外做瀏覽器外掛）。
- 用 AI 從音檔聽寫或對時間。第一次聽無法同步，台語準確度也不足（見 §6）。
- ShazamKit 聽聲音認歌。它需要 Apple Developer 帳號的 App ID 服務，與「不付費」衝突。
- Mac App Store 上架（見 §5）。
- 付費簽章與公證。
- 內建歌詞編輯器。
- 在 repo 裡放任何歌詞資料。
- Windows 或 Linux。

### 什麼情況算失敗（即使技術上能動）

- 擋住點擊，或搶走鍵盤焦點。
- 寫 code 時明顯耗電或拖慢電腦。
- 信心滿滿地顯示錯的歌詞。寧可顯示「找不到字幕」，也不要配到同名的另一首歌。
- 要使用者註冊帳號或申請 API key。

## 4. 使用體驗

### 一首歌的流程

| 畫面 | 出現時機 |
|---|---|
| 片頭字卡 | 第一句歌詞之前，最多顯示前 10 秒 |
| 星星倒數 | 第一句之前，以及長間奏結束前。4 顆星，每 0.8 秒消失一顆，下一行同時排在下方等待 |
| 歌詞變色 | 上下兩行交錯，唱完的那行換成再下一句 |
| 字幕停留 | 一句唱完到下一句之間，唱完的字維持變色狀態 |
| 掌聲字卡 | 長間奏期間，顯示《來賓請掌聲鼓勵》 |
| 找不到字幕 | 短暫提示，然後字幕層保持全透明 |

- 【判斷】「空白的地方」指間奏沒有歌詞的時間，不是螢幕上的空位。
- 【判斷】「偶爾」的預設：只在 10 秒以上的間奏才有資格出現，每次約五成機率，一首歌最多兩次。
- 【判斷】片頭和字卡出現在使用者擺字幕的同一個位置。
- 【判斷】全螢幕 app（例如 Blender）上也要顯示字幕。
- 【判斷】片頭配色有紅、藍兩種，依提案人的兩張截圖，隨歌曲輪替。

### 操作

【判斷】字幕平常完全穿透滑鼠，所以移動字幕需要明確切換：

- 選單列 ♪ 圖示：顯示目前歌曲與歌詞來源、字幕提早或延後、「移動字幕」開關、顯示或隱藏字幕、開啟設定、結束。
- 打開「移動字幕」時，字幕顯示虛線框並可拖曳，關掉後恢復穿透。需要有快速鍵。

### 設定視窗

全部即時預覽，重開 app 後記得：

- 位置與顯示器選擇（多螢幕）。
- 字幕大小、不透明度。
- 未唱與已唱的文字顏色、描邊顏色、描邊粗細。
- 字體。
- 樣式預設：經典 KTV（預設）、霓虹包廂、低調單行、金曲楷體，可在預設上再微調。
- 片頭字卡、星星倒數、掌聲字卡各自開關。
- 歌詞來源開關（見 §5）。
- 開機自動啟動。

視覺參考：`.superpowers/brainstorm/51470-1794135574/content/subtitle-flow-v3.html`。

## 5. 怎麼做

### 技術

- 【判斷】Swift + AppKit 原生 app，常駐選單列，不顯示 Dock 圖示，支援 macOS 14 以上。
- 【判斷】第一版只做 mediaremote-adapter 這一條偵測路徑，AppleScript 只當時鐘。偵測層要隔一層介面，之後補 AppleScript 備援時不用動其他部分。目前只實測過 macOS 26.4.1，README 要標示 14、15 未測試。
- 字幕視窗是 `NSPanel`：borderless + nonactivating、透明背景、`ignoresMouseEvents`、`.screenSaver` level、`.canJoinAllSpaces` + `.fullScreenAuxiliary` + `.stationary`。【實測】繪製約佔 5% CPU。

### 歌曲偵測與時間來源

- 以 [mediaremote-adapter](https://github.com/ungive/mediaremote-adapter)（BSD-3，打包時保留授權聲明）的 stream 模式取得歌名、歌手、長度、播放狀態與來源 app。它透過 `/usr/bin/perl` 載入 framework。【實測】在 macOS 26.4.1 可用。
- 【實測】Spotify 回報給系統的時間不可靠，不能當時鐘：換歌後慢約 0.5 秒，暫停再播放後慢 1.44 秒，快轉後才準（0.03 秒）；切回聽過的歌時時間會過期；暫停瞬間會短暫回報 0。
- **時鐘規則：** Spotify 與 Apple Music 每秒用 AppleScript 讀 `player position`，收到系統事件時也立刻讀一次，偏差超過 0.12 秒才校正，避免畫面抖動。其餘 app 用系統回報的時間。【實測】Spotify 讀取約 23ms，校正後偏差約 0.03 秒，快轉與回到開頭都在 1 秒內跟上。Apple Music 路徑尚未實測。
- `.app` 需要 `NSAppleEventsUsageDescription`。對方第一次會看到「允許控制 Spotify」的提示。不要對沒在執行的播放器發 AppleScript，否則會把它開起來。

### 歌詞來源與比對

- 【決定】LRCLIB（免費、不需 key）與網易雲都預設開啟。網易雲可在設定裡關閉，UI 要說明它是非官方來源、可能隨時失效。
- 【判斷】選用順序：有通過檢查的逐字資料就用逐字；否則用 LRCLIB 的整行歌詞；再否則用網易雲的整行歌詞。作詞作曲可以從網易雲補上。網易雲失敗時靜默退回 LRCLIB，只失去逐字和作詞作曲。
- 歌名要先清理，例如 Spotify 回報「想見你想見你想見你 - 電視劇《想見你》片尾曲」。YouTube 標題更亂，清理規則由實作者設計。
- 【實測】比對容忍度 12 秒太鬆，配到過長度差 11.8 秒的版本，也疑似配到同名的另一首歌。
- 【判斷】比對規則：歌名正規化後（繁簡統一、去掉括號與副標、忽略大小寫）必須相同，長度差必須在 3 秒內。歌手一致就接受；歌手不一致（例如周杰倫與 Jay Chou）或播放器沒提供歌手時，長度差要在 1 秒內才接受。多筆符合時取長度最接近的，都不符合就當作找不到。
- 網易雲資料是簡體，要轉繁體；ICU 的 `Simplified-Traditional` 轉換可用。
- 查過的結果存到本機快取，鍵為歌名、歌手、長度。每首歌的時間微調也要記住。
- 使用者要能在候選版本間手動切換、匯入自己的 `.lrc` 檔。

### 變色時間

- 【實測】把一行的時間平均攤到下一行開始，會把換氣和長音算進去：9 首歌、189 行對照真實逐字時間，句中慢 0.56 秒、句尾慢 0.81 秒。
- **逐行規則：** 每首歌取「行間距 ÷ 字數」的下四分位數當唱速（上限 0.7 秒／字），一行變色時間是 `字數 × 唱速`，不超過到下一行的距離，整體提早 0.25 秒。【實測】句首 −0.16、句中 +0.06、句尾 +0.12 秒。
- 【實測】這是逐行資料的極限：平均絕對誤差仍約 0.6 秒，因為各首歌的 LRC 品質差很多（行首相對真實演唱從 −1.91 到 +0.48 秒）。
- **逐字資料：** 【決定】第一版要做。【實測】網易雲 `https://music.163.com/api/song/lyric/v1?id=<id>&cp=false&tv=0&lv=0&rv=0&kv=0&yv=0&ytv=0&yrv=0` 回傳的 `yrc.lyric` 有逐字時間，格式是 `[行開始ms,行長ms](字開始ms,字長ms,0)字`，16 首常見華語歌中至少 11 首找得到。
- 【判斷】逐字渲染：依每個字實際的起訖時間和畫面上的 x 位置掃過，不再整行線性。簡轉繁要逐段轉換，保留每個字的時間。
- 【判斷】版本檢查：逐字資料要先通過上面的比對規則。同一首歌在 LRCLIB 也有資料時，比較兩邊的行首時間，中位數差超過 1 秒就視為版本不同，改用 LRCLIB 的整行歌詞。【實測】兩邊曾相差 1.91 秒。
- 手動提早或延後要隨手可得，藍牙耳機和資料誤差無法完全自動解決。

### 歌詞解析

- LRC 的空白時間標記代表一句結束，要拿來判斷間奏。
- 開頭的「作词 : xxx」這類資訊不當歌詞顯示，作詞作曲拿去片頭字卡。
- 「男：」「女：」「合：」前綴轉成倒數標記。【實測】只有少數歌有，沒有時只顯示星星。

### 發佈

- 【決定】GitHub 開源，不付費。
- 【判斷】授權採 MIT，和打包的 BSD-3 工具相容。
- 【判斷】主要安裝方式是一行指令從原始碼編譯，本機編譯的 app 不會被 macOS 擋，對方需要 Xcode 開發工具。
- 【判斷】GitHub Releases 另附未公證的 app 當備案。macOS 26 放行未公證 app 的流程，查到的資料互相矛盾，**要實測後才能寫進 README**。
- 上不了 Mac App Store：依賴 Apple 不開放的私有 API。
- Homebrew 官方 cask 需要通過 Gatekeeper，不適用。
- 【判斷】本機重新編譯後簽章會變，macOS 可能要求重新授權控制 Spotify，需要驗證並在 README 說明。

## 6. 風險

| 風險 | 影響 | 對策 |
|---|---|---|
| Apple 再次封鎖私有 API | 偵測不到播放器 | 之後補 AppleScript 偵測備援，只支援 Spotify 與 Apple Music（第一版不做） |
| 網易雲介面失效 | 失去逐字與作詞作曲 | 失敗時靜默退回 LRCLIB，設定可關閉 |
| LRCLIB 沒有的歌 | 沒字幕 | 明確顯示找不到，提供匯入 .lrc |
| 台語歌 | 覆蓋率與準度不穩 | 實測《茫茫到深更》《夢中的情話》有資料，《媽媽我愛您》沒有。Breeze-ASR-26 連口語都有約 30% 字錯誤，所以不走聽寫 |
| 歌詞版權與預設使用非官方介面 | 公開專案的法律風險 | repo 不放歌詞，只在執行時由使用者端查詢；README 說明資料來源，使用者可關閉網易雲 |
| YouTube 時間準度 | 字幕可能偏移 | 尚未實測，先用手動微調 |

## 8. 工程要求

- 依提案人的全域規則：TDD、80% 測試覆蓋率、不可變資料、小檔案、完整錯誤處理。
- 純邏輯部分（LRC 解析、唱速估算、畫面狀態機、比對規則、標題清理）要有單元測試，可用 `spike/` 量到的數字當測試資料。
- `spike/` 是用完就丟的實驗，不進正式 repo，只保留驗證過的做法。`.superpowers/` 也要加進 `.gitignore`。
